## Контекст проекта
CamFusion - это промышленная система маркировки и агрегации продукции с использованием камер, работающая по стандарту GS1. Система отслеживает иерархию: Продукт → Короб → Паллета.

**Текущая архитектура:**
- CC.UI (WPF презентационный слой)
- CC.Core (бизнес-логика)
- CC.Data (Entity Framework Core, SQL Server)
- JsonParser, SocketManager (вспомогательные сервисы)

## Суть изменений

### БЫЛО (старая логика):
- 3 камеры сканируют коды продуктов и короба
- Приходит пакет: код короба + коды продуктов
- Короб сразу создается в БД
- Оператор вручную закрывает паллету когда накопилось нужное количество коробов
- Возможность добавления продуктов вручную

### СТАЛО (новая логика):
Система из 5 камер с поэтапной обработкой:

**Камера 1 (Статистическая):**
- Сканирует по одному коду продукта
- Увеличивает счетчик на главном экране
- НЕ создает записи в БД, только статистика

**Камеры 2-3 (Ведущая-Ведомая, формирование короба):**
- Присылают пакет из N кодов продуктов (например, 20 штук)
- Количество продуктов в коробе задается в настройках задания
- После получения пакета:
  - Формируется этикетка короба
  - Короб создается ВИРТУАЛЬНО (временное хранилище)
  - Коды продуктов хранятся временно, привязанные к виртуальному коробу
  - Ожидается подтверждение печати этикетки

**Камеры 4-5 (Ведущая-Ведомая, верификация короба):**
- Присылают пакет из 2 кодов:
  1. Код напечатанной этикетки короба
  2. Код одного продукта из этого короба
- Задачи верификации:
  - Проверить код этикетки короба регулярным выражением (использовать существующую валидацию)
  - Проверить, что код продукта принадлежит виртуальному коробу с данной этикеткой
  - После успешной проверки: короб переходит из виртуального состояния в реальное (сохраняется в БД)

**Закрытие паллеты:**
- Оператор закрывает паллету вручную когда накопилось нужное количество коробов
- Печатается паллетная этикетка
- Опционально: добавление продуктов/коробов вручную
- Остановка задания

### 4. Алгоритм работы (пошаговый flow)

**Шаг 1: Инициализация задания**
```
1. Оператор создает задание с параметрами:
   - GTIN продукта
   - Lot number
   - Количество продуктов в коробе (ProductsPerBox)
   - Количество коробов на паллете
2. Система генерирует шаблоны кодов
3. Инициализируется счетчик статистики = 0
4. АВТОМАТИЧЕСКИ создается первая паллета:
   - Pallet.TaskId = текущее задание
   - Pallet.Status = InProgress
   - Pallet.CreatedAt = DateTime.Now
   - Сохранение в БД
5. Задание готово к работе
```

**Шаг 2: Камера 1 - Статистика**
```
1. Получен код продукта
2. Валидация формата кода (регулярное выражение)
3. StatisticsCounter++
4. Обновление UI (без записи в БД)
```

**Шаг 3: Камеры 2-3 - Формирование короба**
```
1. Получен пакет из N кодов продуктов
2. Проверка:
   - Количество кодов == ProductsPerBox
   - Все коды уникальны
   - Все коды соответствуют текущему заданию (GTIN, формат)
3. Создание VirtualBox:
   - Генерация уникального Id
   - Сохранить коды продуктов (JSON или строка)
   - Status = Created
4. Генерация кода этикетки короба (GS1-compliant)
5. VirtualBox.BoxLabelCode = сгенерированный код
6. VirtualBox.Status = LabelGenerated
7. Сохранение в память (ConcurrentDictionary) для быстрого доступа
8. Async сохранение в БД с IsInMemory = true
9. Отправка на принтер этикетки короба
```

**Шаг 4: Камеры 4-5 - Верификация**
```
1. Получен пакет: (boxLabelCode, productCode)
2. Валидация boxLabelCode регулярным выражением
3. Поиск VirtualBox:
   a. Сначала в памяти (ConcurrentDictionary)
   b. Если не найден → поиск в БД (может быть expired)
4. Проверка:
   - VirtualBox существует
   - VirtualBox.Status == LabelGenerated (или Expired для ручной обработки)
   - productCode присутствует в VirtualBox.ProductCodes
5. Если все проверки пройдены:
   a. Создать реальный Box в БД:
      - BoxCode = boxLabelCode
      - PalletId = текущая паллета (Status = InProgress)
      - VirtualBoxId = VirtualBox.Id
   b. Создать Product записи для всех кодов из VirtualBox.ProductCodes:
      - ProductCode = код из списка
      - BoxId = созданный Box.Id
   c. Обновить VirtualBox:
      - Status = Verified
      - VerifiedAt = DateTime.Now
      - IsInMemory = false
   d. Удалить из памяти
   e. Обновить счетчики паллеты
   f. Сохранить в БД для истории
6. Если проверки не прошли:
   - Логирование ошибки с деталями
   - Уведомление оператора через UI
   - VirtualBox остается в текущем статусе
   - Можно показать в UI списке проблемных коробов
```

**Шаг 5: Закрытие паллеты**
```
1. Оператор нажимает "Закрыть паллету"
2. Проверки:
   - Нет ожидающих верификации виртуальных коробов в памяти
   - Количество коробов соответствует плану (или оператор подтверждает отклонение)
3. Генерация кода паллетной этикетки
4. Печать паллетной этикетки
5. Обновление текущей Pallet:
   - Status = Closed
   - ClosedAt = DateTime.Now
   - PalletCode = сгенерированный код
6. Опционально: форма для ручного добавления продуктов/коробов
7. Если задание продолжается:
   - Создание новой паллеты для следующих коробов
   - Новая Pallet.Status = InProgress
```

**Шаг 6: Остановка задания**
```
1. Проверка состояния:
   - Все паллеты закрыты ИЛИ оператор подтверждает остановку с незакрытыми паллетами
   - Если есть паллета InProgress → её статус остается InProgress (для возможности продолжения)
2. Очистка памяти:
   - Все активные VirtualBox переносятся в БД как Expired/Timeout
   - Очистка ConcurrentDictionary
3. Финализация открытых паллет (опционально):
   - Если оператор решает закрыть все → Status = Closed для всех InProgress
   - Если оставить открытыми → они остаются InProgress для продолжения работы
4. Экспорт данных:
   - Генерация GS1-compliant JSON для всех закрытых паллет
   - Экспорт в network share
5. Обновление задания:
   - ReportTask.Status = Stopped (если полностью остановлено)
   - ReportTask.Status = Paused (если можно продолжить)
6. Возможность продолжения:
   - Оператор может перезапустить задание
   - Система подхватывает существующие паллеты InProgress
   - Продолжение работы с того же места
```

### 5. Обработка ошибок

#### 5.1 Ошибки камеры 1
- Невалидный формат кода → игнорировать, логировать
- Дубликат кода → только статистика, не критично

#### 5.2 Ошибки камер 2-3
- Неверное количество кодов в пакете → отклонить весь пакет
- Дубликаты внутри пакета → отклонить пакет
- Код уже использован в другом коробе → отклонить пакет
- Невалидный GTIN → отклонить пакет

#### 5.3 Ошибки камер 4-5
- Невалидный код этикетки короба → отклонить, уведомить оператора
- VirtualBox не найден → возможно, таймаут или ошибка печати
- productCode не найден в VirtualBox → несоответствие, отклонить
- Дубликат верификации → игнорировать повторную верификацию

#### 5.4 Таймауты
- VirtualBox старше N минут без верификации → пометить как expired
- Возможность ручной верификации/удаления expired коробов

## Управление паллетами

**ВАЖНО:** Паллета создается автоматически при создании задания и сохраняется в базе данных со статусом "InProgress" (не завершена).

**Принцип работы:**
- При создании ReportTask автоматически создается первая Pallet с привязкой к этому заданию
- Pallet.Status = InProgress (или аналогичный статус "незавершено")
- Если происходят неполадки (ошибки камер, сбои системы), паллета остается в БД
- Оператор может:
  - Остановить задание
  - Исправить ошибки
  - Продолжить выполнение того же задания с той же паллетой
- Только после явного закрытия оператором: Pallet.Status = Closed

**Изменения в Pallet entity:**
```csharp
enum PalletStatus 
{
    InProgress,    // Активная паллета, принимает коробы
    Closed,        // Закрыта оператором, больше не изменяется
    Error          // Паллета с ошибками, требует вмешательства
}

Pallet:
- Status (PalletStatus) - статус паллеты
- CreatedAt (DateTime) - время создания
- ClosedAt (DateTime?) - время закрытия
- ErrorMessage (string?) - описание ошибки если Status = Error
```

## Хранение виртуальных коробов

**Двухуровневая система хранения:**

### 1. Активные виртуальные коробы (In-Memory + кэш)
- Хранятся в быстром доступе (Dictionary, ConcurrentDictionary)
- Используются для текущей работы
- Статус: Created, LabelGenerated (ожидают верификации)
- Быстрый поиск по BoxLabelCode и ProductCode

### 2. Expired виртуальные коробы (Database)
- Автоматически переносятся в БД при истечении таймаута
- **НЕ удаляются, а архивируются** для аудита
- Статус: Expired, Timeout
- Цель: историческая трассировка, анализ проблем, восстановление данных

**Обновленная VirtualBox entity:**
```csharp
enum VirtualBoxStatus
{
    Created,           // Только создан
    LabelGenerated,    // Этикетка сгенерирована, ожидает верификации
    Verified,          // Успешно верифицирован и конвертирован в реальный Box
    Expired,           // Истек таймаут, перенесен в БД
    Timeout,           // Не дождался верификации
    Error              // Ошибка при обработке
}

VirtualBox:
- Id (Guid)
- TaskId (FK к ReportTask)
- BoxLabelCode (string)
- ProductCodes (string) - JSON массив или comma-separated
- CreatedAt (DateTime)
- ExpiredAt (DateTime?) - когда стал expired
- VerifiedAt (DateTime?) - когда прошел верификацию
- Status (VirtualBoxStatus)
- IsInMemory (bool) - флаг для быстрой фильтрации активных
- ErrorMessage (string?) - описание ошибки
- TimeoutReason (string?) - причина таймаута
```

**Алгоритм работы с виртуальными коробами:**

```
1. Камеры 2-3 создают VirtualBox:
   - Сохраняется в памяти (ConcurrentDictionary)
   - Async сохраняется в БД с IsInMemory = true
   - Status = LabelGenerated

2. Фоновая задача проверяет таймауты (каждую минуту):
   - Находит VirtualBox где (DateTime.Now - CreatedAt) > Timeout
   - Обновляет Status = Expired
   - Удаляет из памяти
   - Обновляет в БД: IsInMemory = false, ExpiredAt = DateTime.Now

3. Камеры 4-5 верифицируют VirtualBox:
   - Поиск сначала в памяти
   - Если не найден в памяти → поиск в БД (возможно, уже expired)
   - Если expired → можно обработать или показать ошибку
   - Успешная верификация → конвертация в реальный Box

4. Пользователь может:
   - Просматривать expired коробы (отдельный UI раздел)
   - Анализировать: когда, почему произошел таймаут
   - Восстанавливать данные при необходимости
   - Экспортировать историю для аудита
```

**Преимущества подхода:**
- Быстрая работа с активными коробами (in-memory)
- Полная история для аудита и отладки
- Возможность анализа проблем производства
- Восстановление после сбоев
